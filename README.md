# Переключение Ethernet / VPN в Vivaldi

Два локальных SOCKS5-прокси на 3proxy 0.9.5. Сервисы работают в Docker
с сетью хоста, без изменения маршрутов, firewall и NetworkManager.

| Профиль FoxyProxy | Тип | Адрес | Порт | Выход |
|---|---|---|---|---|
| Ethernet enp5s0 | SOCKS5 | 127.0.0.1 | 1081 | Ethernet, минуя системный VPN |
| VPN vpn0 | SOCKS5 | 127.0.0.1 | 1082 | VPN |

Логин и пароль не нужны. Порты доступны только локально, но пользоваться ими
может любой процесс/пользователь этой машины. Это не разграничение доступа
между локальными пользователями.

## Один раз в Vivaldi

Сначала из корня репозитория получить актуальный общий файл:
`sh scripts/foxyproxy.sh > foxyproxy.json`.
`examples/foxyproxy.json` — только пример экспорта; актуальный файл генерируется
в корень как `foxyproxy.json` и исключён из Git через `.gitignore`.
Для этой команды на хосте нужны Python 3 (без сторонних пакетов) и Docker Compose.

1. Установить **FoxyProxy Standard** из Chrome Web Store:
   https://chromewebstore.google.com/detail/foxyproxy-standard/gcknhkkoolaabfmlnjonogaaifnjlfnp
   Проверить, что издатель — FoxyProxy. Закрепить значок расширения на панели.
2. Если FoxyProxy уже используется — сначала экспортировать его настройки.
   **Импорт `foxyproxy.json` заменяет весь список старых прокси и правил.**
   При включённой синхронизации изменения могут попасть на другие устройства.
3. Выбрать в меню расширения **Disable**, открыть настройки FoxyProxy,
   затем **Options → Import**, выбрать `foxyproxy.json` из этой папки.
   Это обычный импорт, не «Import from older versions». На вкладке
   **Proxies** проверить оба профиля и нажать **Save**.
4. Если старые профили нужно сохранить, вместо импорта добавить две записи
   вручную по таблице выше. Выбрать именно SOCKS5, без авторизации.

Профили подготовлены для текущей схемы FoxyProxy Standard. Если названия
пунктов в установленной версии отличаются, ручное добавление по таблице
не зависит от формата импорта.

## Каждый день

Нажать значок FoxyProxy → **Ethernet enp5s0** или **VPN vpn0**, затем
перезагрузить нужную страницу. Явный выбор профиля действует на запросы
браузера в целом, а не изолирует одну вкладку. Уже открытые соединения,
WebSocket, загрузки и страницы автоматически не мигрируют.

**Disable / без прокси — это системная маршрутизация.** На момент настройки
маршрут по умолчанию идёт через `vpn0`; это НЕ режим Ethernet.

Для автоматического выбора по сайту открыть профиль → **Include** и добавить
wildcard, например `*://example.org/*` и `*://*.example.org/*`, затем выбрать
режим **Proxy by Patterns**. Это пример, готовых правил для сайтов в импорте нет.
Не добавлять один домен сразу в два профиля. Сторонние домены сайта (CDN,
авторизация, API, картинки) требуют отдельных правил; непокрытые запросы идут
по маршруту режима по умолчанию. Если важно направить весь трафик страницы
через один выход, надёжнее явно включить профиль для всего браузера.

Проверить в браузере: https://www.cloudflare.com/cdn-cgi/trace — поле `ip=`.
Адрес и страну также можно проверить на предпочитаемом сервисе проверки IP.

## DNS, безопасность и ограничения

- `-Deenp5s0` / `-Devpn0` используют Linux `SO_BINDTODEVICE`.
  При отсутствии интерфейса нет переключения на другой выход. Если интерфейс
  существует, но не имеет маршрута/связности, запрос завершится ошибкой/таймаутом.
- Встроенные DNS-сокеты этой версии 3proxy не привязываются параметром `-De`.
  Поэтому у каждого процесса свой DNS-кэш и TCP-релей на `127.0.0.1:11081`
  либо `127.0.0.1:11082`, который выходит к `1.1.1.1:53` через тот же интерфейс.
  Системный DNS не используется для разрешения имён, переданных SOCKS-прокси.
- Cloudflare получает DNS-запросы. DNS по TCP **не зашифрован**. Если сеть
  блокирует внешний TCP/53, разрешение имён через профиль перестанет работать.
- В Chromium/Vivaldi SOCKS5 передаёт имя прокси; флаг `proxyDNS` в импорте
  не является глобальной защитой DNS браузера. Secure DNS, предзагрузка,
  расширения и другие фоновые механизмы требуют отдельной проверки.
- Проксируются IPv4 TCP-соединения. SOCKS BIND/UDPASSOC запрещены.
  Это не VPN для всего браузера/ОС: WebRTC, UDP, расширения, исключения прокси,
  локальные адреса и служебный трафик могут обрабатываться отдельно.
  Для чувствительных сценариев отключить WebRTC non-proxied UDP в настройках
  приватности Vivaldi, если такой пункт есть, и проверить утечки отдельно.
- Не включать в расширении прямой fallback на случай ошибки прокси.
- Контейнеры работают не от root и без NET_ADMIN/privileged.
  Корневая ФС доступна для записи; общий шаблон подключён только для чтения.
  Стартовый скрипт проверяет параметры, создаёт конфиг в `/tmp` и через `exec`
  заменяется 3proxy, который получает сигналы Docker напрямую.
  Разрешена только capability NET_RAW для привязки к устройству на ядрах,
  где она необходима. Host network нужен, чтобы видеть настоящие интерфейсы.
- Журналы не содержат URL, имён сайтов и адресов назначения; ротация 2 × 5 MB
  для каждого контейнера. Это не гарантия анонимности и не защита от fingerprinting.

## Управление

Compose-проект называется `3proxy`, контейнеры — `3proxy-ethernet` и
`3proxy-vpn`. Имена сервисов для команд `docker compose exec` остались
`ethernet` и `vpn`.

Общий шаблон 3proxy встроен в `configs.proxy-template.content` файла
`compose.yaml` (нужен Docker Compose 2.23.1 или новее) и подключён через
`target: /etc/3proxy/3proxy.cfg.tmpl`. Параметры интерфейса и портов задаются
в `environment` сервиса; отдельные `.cfg` не нужны. Стартовый скрипт использует
Python 3 из образа. Для чтения Compose YAML внутри контейнера установлен PyYAML. `read_only: true` для корневой ФС
не используется: установленный Compose не поддерживает его совместно с
`configs.content`.

Структура репозитория:

```text
.
├── compose.yaml                 # сервисы и встроенный шаблон 3proxy
├── .dockerignore                # исключения контекста сборки
├── .gitignore                   # в том числе сгенерированный foxyproxy.json
├── README.md
├── Makefile                     # тесты и публикация релиза
├── src/proxy.py                 # запуск прокси и генерация экспорта
├── scripts/
│   ├── check.sh                 # проверка выходов с хоста
│   ├── foxyproxy.sh             # общий экспорт с хоста
│   ├── release.py               # проверки, Git и публикация образа
│   └── test.sh                  # запуск тестов
├── tests/
│   ├── test_proxy.py
│   ├── test_compose_source.py
│   └── test_release.py
├── docker/Dockerfile            # сборка образа
└── examples/foxyproxy.json       # пример, не актуальная конфигурация
```

Сборка в Compose использует `build.context: .` и
`build.dockerfile: docker/Dockerfile`.

Все команды ниже выполнять из корня репозитория:

```sh
docker compose up -d --build      # собрать / запустить
docker compose ps               # состояние
docker compose logs --tail 50   # журнал
sh scripts/check.sh             # HTTPS + SOCKS DNS, внешний IP каждого выхода
docker compose up -d            # применить изменения конфигов в compose.yaml
docker compose down             # остановить и удалить только эти контейнеры
```

`restart: unless-stopped` обеспечивает автозапуск вместе с Docker, если
контейнеры не были явно остановлены. Docker на этой машине включён в автозагрузку.
Остановка прокси не меняет маршруты ОС; выбранный в FoxyProxy профиль перестанет
открывать сайты, пока не запустить прокси или не переключить режим расширения.

Конфиги не зависят от отдельных файлов в папке проекта: Compose создаёт их
из встроенного `configs.*.content`. Для управления сервисами сохранять `compose.yaml`,
а для пересборки — также `docker/Dockerfile`, `.dockerignore`, `src/proxy.py`
и `scripts/foxyproxy.sh`.

Переименование интерфейсов требует изменения `PROXY_INTERFACE` сервиса
и применения через `docker compose up -d`. IP-адреса не зафиксированы,
смена DHCP не требует перегенерации конфигурации.

### Переход со старого имени проекта

Если контейнеры проекта `interface-proxy` ещё работают, сначала остановить их,
затем запустить новый проект. Иначе старые контейнеры займут те же SOCKS/DNS-порты.
Из корня репозитория:

```sh
docker compose -p interface-proxy down
docker compose up -d --build
```

Остановка затронет только старый Compose-проект; текущие соединения через него
оборвутся. Каталог репозитория теперь называется `3proxy`; пути сборки и скриптов
относительные, их менять не требуется. Имя внутренней утилиты `interface-proxy`
и тег образа `local/interface-3proxy:0.9.5` не зависят от имени проекта и сохранены.

## Релиз и публикация образа

Из корня репозитория:

```sh
make release TAG=v1.0.0
```

Нужны Git с настроенными `user.name`/`user.email` и доступом на запись к `origin`,
Python 3, GNU Make, работающий Docker и Compose. На хосте без PyYAML четыре
теста чтения YAML будут пропущены; для запуска всех тестов установить
`python3-yaml`. Образ содержит эту зависимость независимо от хоста.

Один раз авторизоваться в обоих registry:

```sh
docker login docker.io --username r4venme
docker login ghcr.io --username r4ven-me
```

Пароли/токены вводить в запросе Docker, не сохранять в репозитории.
Для GHCR нужен токен с правом `write:packages` и доступом к целевому пакету;
для Docker Hub — права на публикацию в `r4venme/3proxy`.

Команда выполняет последовательно:

1. Проверяет `TAG`, текущую Git-ветку, отсутствие незавершённых Git-операций,
   Git identity, доступность Docker и отсутствие Git-тега локально и на `origin`.
2. Запускает тесты и проверяет Compose, затем **один раз** собирает образ
   из `docker/Dockerfile` для архитектуры текущего Docker builder.
3. Делает `git add --all` и коммит `chore(release): <TAG>`. Включаются **все
   неигнорируемые изменения и новые файлы** репозитория — перед релизом проверить
   `git status`, чтобы не отправить личные данные. Если изменений нет, используется
   текущий коммит без создания пустого.
4. Создаёт аннотированный Git-тег с именем из `TAG`, атомарно отправляет текущую
   ветку и тег в `origin`, без force-push. Detached HEAD не поддерживается.
5. Отправляет один и тот же собранный образ под четырьмя именами:

```text
docker.io/r4venme/3proxy:<TAG>
docker.io/r4venme/3proxy:latest
ghcr.io/r4ven-me/3proxy:<TAG>
ghcr.io/r4ven-me/3proxy:latest
```

`TAG` обязателен; `latest` зарезервирован и обновляется автоматически.
Релиз не пересоздаёт запущенные прокси. Конфиги и настройки браузера не меняются.

Публикация между Git и двумя registry **не атомарна**. При ошибке выполнение
останавливается без автоматического удаления коммита/тега или отката образов.
После начала публикации перед повтором проверить, что уже отправлено.
Если Git уже опубликован, но упал registry push, можно повторить необходимые
`docker push` для четырёх имён выше: образ и все теги остаются локально.
Повторный `make release` с существующим Git-тегом будет отклонён, тег не перезаписывается.

Только тесты: `make test`. Показать команды Make без выполнения:
`make -n release TAG=v1.0.0` (это показывает вызов скрипта, не полный план его шагов).

## Добавить интерфейс / сервис

Добавить блок в `services` в `compose.yaml`, например (Wi-Fi должен быть подключён):

```yaml
  wifi:
    <<: *proxy
    container_name: 3proxy-wifi
    hostname: 3proxy-wifi
    environment:
      PROXY_INTERFACE: wlp4s0
      PROXY_PORT: "1083"
      PROXY_NAME: Wi-Fi
      PROXY_COLOR: "#ebcb8b"
```

Новый конфиг 3proxy писать не нужно. Обязательны только `PROXY_INTERFACE`
и `PROXY_PORT`; имя по умолчанию равно интерфейсу, цвет — `#88c0d0`.
DNS-порт по умолчанию равен SOCKS-порту + 10000 (`1083 → 11083`).
Опционально задать `PROXY_DNS_PORT` явно и `PROXY_DNS_SERVER` (IPv4, по умолчанию
`1.1.1.1`). Все SOCKS- и DNS-порты должны быть уникальны на хосте, диапазон
1024–65535. При SOCKS-порте выше 55535 нужно явно указать DNS-порт.

Проверить параметры и коллизии между сервисами, затем запустить:

```sh
sh scripts/foxyproxy.sh          # общий JSON, проверка параметров и конфликтов портов
docker compose up -d --build
sh scripts/check.sh             # автоматически проверяет все описанные выходы
```

Межсервисные конфликты проверяет команда `sh scripts/foxyproxy.sh`; отдельный
контейнер проверяет только свои параметры. Занятость портов другими программами
на хосте нужно проверять отдельно. Удалять сервисы через
`docker compose up -d --remove-orphans`, чтобы старые контейнеры не остались работать.

## Получить конфиг FoxyProxy

При каждом старте контейнер пишет в stdout JSON **только своего профиля**
между маркерами `--- FoxyProxy import` и `--- End FoxyProxy import ---`.
Посмотреть вывод: `docker compose logs --no-log-prefix ethernet`.

Повторно получить чистый JSON без перезапуска и служебных строк:

```sh
docker compose exec -T ethernet interface-proxy foxyproxy
docker compose exec -T vpn interface-proxy foxyproxy
```

Для **всех** сервисов вместе, включая добавленные пользователем, из любого
прокси-контейнера:

```sh
docker compose exec -T ethernet foxyproxy.sh
docker exec 3proxy-ethernet foxyproxy.sh
docker exec 3proxy-ethernet foxyproxy.sh > foxyproxy.json
```

Команда внутри контейнера читает `compose.yaml`, подключённый через `configs`
только для чтения в `/etc/3proxy/compose.yaml`. Docker CLI/socket не нужны.
Экспортируется базовый Compose-файл, а не фактическое состояние контейнеров.
После добавления сервиса применить `docker compose up -d`, чтобы обновить
подключённый файл. YAML anchors поддерживаются; overrides и подстановки из
`.env` внутри контейнера не обрабатываются. Неразрешённые подстановки в `PROXY_*`,
`env_file`, `extends` и `include` отклоняются с ошибкой вместо неточного JSON.
Для таких конфигураций передать разрешённый JSON с хоста:

```sh
docker compose config --format json | docker exec -i 3proxy-ethernet interface-proxy foxyproxy --compose
```

На хосте из корня репозитория:

```sh
sh scripts/foxyproxy.sh
sh scripts/foxyproxy.sh > foxyproxy.json
```

Общая команда читает `docker compose config --format json`: учитывает
подстановки Compose и overrides, экспортирует сервисы из полученного описания,
не требует запущенных контейнеров и не подключает Docker socket к контейнеру.
Сервисы без `PROXY_INTERFACE` игнорируются. Профиль означает описанную
конфигурацию, а не проверенную доступность интерфейса; её проверяет
`sh scripts/check.sh`.

**Импорт любого JSON заменяет старый список FoxyProxy.** Чтобы не потерять
остальные профили, импортировать общий файл, а не JSON одного контейнера.
Генерация не меняет настройки браузера и не создаёт правила сайтов.
После изменения параметров и `docker compose up -d` нужно заново получить
и импортировать JSON. Если менялся `src/proxy.py`, требуется пересборка образа.

Тесты: `sh scripts/test.sh`. Скрипт запускает `unittest discover -s tests`
с `src` в `PYTHONPATH` и сам определяет корень репозитория независимо от текущего
каталога. Из другого каталога указывать абсолютный путь к `scripts/test.sh`.

## Что проверено при настройке

- `docker compose config --quiet`, сборка и запуск обоих контейнеров.
- HTTPS по доменному имени через каждый SOCKS5 с передачей DNS прокси.
- Разные внешние IPv4 для Ethernet и VPN.
- Все четыре слушающих порта привязаны только к `127.0.0.1`.
- Отдельный временный экземпляр с несуществующим устройством отклоняет
  соединение; недоступный DNS-релей не даёт успешно открыть сайт.
- Браузер и расширение автоматически не изменялись; импорт и проверку в Vivaldi
  нужно выполнить вручную. Перезагрузка ОС и реальное отключение VPN не проводились.

Исходники 3proxy зафиксированы коммитом `f23fc4fc4458606a257a9f26bc37251fc60e1cc7`.
Схема FoxyProxy проверена по upstream `ab9e6d5`:
https://github.com/foxyproxy/browser-extension/blob/ab9e6d5/src/content/schema.json
